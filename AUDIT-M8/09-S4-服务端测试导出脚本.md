**B3 · `serve.sh stop` 不核验 kill 结果，失败也报「已停止」并删掉 pidfile → 看门狗变不可寻址孤儿**

- **位置**：`scripts/serve.sh:26`（`alive && kill -- -"$(cat "$PIDFILE")" 2>/dev/null; sleep 0.5; rm -f "$PIDFILE"`，随后 `healthy && echo 警告 || echo "已停止"`）｜`alive()`（`:10`）只是 `kill -0` 存在性检查；守护结构见 `:16-21`（`setsid bash -c 'echo $$ > pidfile; while true; … sleep 2; done'`），**唯一句柄就是这个 pidfile**。
- **证据（效率透镜探针 `probes/S4/probe_scripts.py`，`PORT=8099` + 假 pidfile 指向活进程，未碰 `:8094`）**：
  ```
  dummy pid=998104 alive=True
  serve.sh stop → exit=0 stdout='已停止' stderr=''
  pidfile 还在吗: False ｜ dummy 还活着吗: True
  ```
- **问题（机制）**：kill 失败（pidfile 陈旧/被手工删过、PID 已回收、组不存在）或根本没执行时，`2>/dev/null` 吞错 → 无条件 `rm -f` → 报「已停止」+ exit 0。用户以为停了 → 再 `run` → **第二个看门狗**上马；抢不到 `:8094` 的那个每 2 s 失败一次并往 `serve.log` 写两行，直到重启机器。次生：`kill -- -PID` 打**进程组**，PID 被回收给 NAS 上另一 setsid 守护时会杀掉无关进程组（质量 #17 同点，confidence medium）。
- **冲突裁决记录**：高度透镜附注 5 判 `serve.sh`「本批零缺陷发现」（setsid+while true 自愈守护、pidfile、整组杀＝M7 已拍板运维口径）。**裁决：机制本身不议（不挑战 M7 口径），只报失败分支的静默处理**——探针实证的「假成功 + 句柄丢失」是 correctness 面，两透镜（效率 S4-E01 + 质量 #17）同点，聚合**升格为真 Bug**。
- **违反规则**：Make public APIs … hard to misuse（`stop` 的成功语义不可信）；Separate commands from queries / 静默兜底家族。
- **修法**：kill 后 `kill -0` 复核，仍在则**保留 pidfile** 并 `exit 1`；pidfile 存「pid + 启动时间（`ps -o lstart=`）」并在 `alive` 里比对（顺带解决 PID 复用）；`rm -f` 只在确认已死时执行；`stop` 前要求 `healthy` 判据与 `alive` 一致。
- **severity：中（运维；静默假成功 + 潜在误杀）｜ effort：低｜ 来源：效率 S4-E01（探针）+ 质量 #17（同点）｜ confidence：high（失败分支探针实证）**

- **位置**：`server/api/export.py:30`：`'attachment; filename="%s"; filename*=UTF-8\'\'%s' % (name_ascii, quote(name_utf8))`——`name_ascii` 由 `core/export.py:168/171` 用库内 `scene_no` 原值拼成（`scene_no` 只校验非空+唯一，S1-A03 已记）。
