## 一、真 Bug（6 条，按严重度排序）

> 本批 6 条 Bug 均**无数据损坏路径**（持久化契约归服务端批次）；影响面为 UI 顺序 / 状态 / 交互态。证据级别：B1 为静态代码路径 + **离线顺序模型推演**；B2/B3 为静态可证；B4/B6 为静态路径推演（未真机复现）；B5 为静态可见。复现建议随条给出。

### 中危（3 条）

**B1 · 活体块库卡没有「置顶块退出拖序」护栏（该规则只活在已退役的热盒条里）→ 拖置顶块静默改写 `position`，取消置顶后跳位**

- **位置**：`web/js/bc-list.js:33-51`（`gripOf` 无条件 `grip.draggable = true`（:36）、`dragstart` 无条件 `dragging = {id: b.id}`（:43））、`:53-77`（`bindRowDrop` 的 `dragover/drop` 守卫只有 `dragging.id === b.id`，:55 / :65）、`:79-117`（`bindRowsDrop` / `bindHeadDrop` 同无 pinned 守卫）。**对照（死件里才有护栏）**：`web/js/blocks.js:271-273`（`c.draggable = !b2.pinned`）+ `:276/:291/:301` 四处 `|| b2.pinned` 守卫，注释自述规则与 `AGENTS.md:60` ② 的 B7 定案「置顶块不可拖、不作落点」。
- **两条序不同源（机制）**：显示序 `blocks.js:132-147 sortedBlocks()`（**置顶最前** → 分类序 → `byPosition`）；落点索引 `bc-list.js:71-73` 走 `siblingList(cid)`＝**纯 position 序**（`blocks.js:46-51`）。同一分类内两序不一致时，「拖到 P 之前」在 position 空间里指的不是用户看到的位置。
- **证据（离线推演，`probes/F3-order-probe.mjs` → `.out`）**：夹具 `A(未置顶,pos0) · P(置顶,pos1) · B(未置顶,pos2)`，显示序 `P|A|B`、position 序 `A|P|B`：
  - ① 把 B 拖到 P 上半（视觉应落 P 之前）→ 显示序**原地不动**，position 序被改成 `A|B|P`（库已改、视觉零变化）；
  - ② 拖置顶块 P 到 B 下方 → 显示序不变，**P 的 position 被静默改到末尾**；
  - ③ 取消 P 的置顶 → 显示序变 `A|B|P`，P「凭空跳位」。
- **影响**：用户看到的「没反应」与库里的真实改动不一致（静默数据变更）；取消置顶后块位跳变。`Ctrl+Z` 可救，但用户不知道需要撤。
- **修法（二选一，需一次拍板；推荐 ①）**：① **回到 B7 口径**——`bc-list.js:36/43/55/65` 各加一行 pinned 判断；更稳妥是上收数据层：`blocks.js` 出 `canDrag(b)/canDropOn(b)`，或在 `moveBlockTo` 内拒绝「源或落点为置顶」并 toast。② **让两序同源**（深修，入立项 L2）。
- **severity：中危｜ effort：small（走 ①）｜ 来源：复用(BUG-F3-1) + 高度(BUG-F3-A1)｜ confidence：medium-high**

**B2 · 删除块后的 Ctrl+Z 不还原位置（块回到分类末尾）——违反「Ctrl+Z 完整还原」口径**

- **位置**：`web/js/blocks.js:86-101`（`deleteBlockWithUndo`，其 undo 在 `:92-95` 只发 `{action:'create', text, category_id}` + `{action:'pin'}`，**没有 position**；而 `b2.position` 在删之前手边就有——同文件 `:54-58` 的 `moveBlockTo` 就用 `oldPos` 做撤销）。服务端：`server/core/prompts.py:372-384 block_create` 不接受 position（落点写死 `MAX(position)+1`＝末尾）；`:400-425 block_update` **支持** position。
- **表现**：删掉分类中间（或置顶）的一个块 → Ctrl+Z → 块回来了但落在**该分类末尾**；随后 `siblingList` 拖放索引与卡片列表序都与用户预期不符。`DO_NOT_FLAG A2` 记载的产品口径是「删除不弹确认（即时删 + Ctrl+Z 完整还原 + 痕迹 + 每日快照三层兜底）」——此处第一层就打了折。
- **修法**：undo 里 create 之后补一次 `{action:'update', id: res.block.id, category_id: b2.category_id, position: b2.position}`（服务端已支持），或给 `block_create` 加可选 position。
- **severity：中危｜ effort：small｜ 来源：质量(BUG-F3-1)｜ confidence：high（静态可证）**

**B3 · 「写成功」与「重取缓存成功」被绑成一个 reject → 报假失败 + 撤销断链 + 本地 cache 仍是旧值**

- **位置**：`web/js/blocks.js:124-129`（`const res = await api.blockOp(payload); await ensureBlocks(true); … return res;` 两段 await 无 try 隔离）；受害调用方 `blocks.js:59-68 / 72-84 / 86-101`、`bc-ops.js:34-47 / 59-70 / 84-93 / 113-121`（8 处 catch **全部只** `toast('…失败：'+err.message,'err')`，无「可能已写入」分支）。
- **机制**：写已落库、随后的 `GET /api/blocks` 若失败（服务端 500 / 连接抖动 / 被刷新打断），`blockOp` 整体 reject → 弹「移动失败 / 删除失败 / 建分类失败」；而 `recordUndo` 位于 `blockOp` **之后** → 这条写的撤销条目也不登记 ⇒ **服务端已写、UI 说失败、Ctrl+Z 撤不回、画面与库不一致**（直到下一次写或刷新）。
- **修法**：写/重取解耦——重取失败只当「缓存过期」（标脏 `cache=null` + 轻提示），不把写的结果判成失败；撤销登记移到写响应之后、重取之前。
- **severity：中危｜ effort：small｜ 来源：效率(BUG-F3-2)｜ confidence：high**

### 低危（3 条）

**B4 · 写后强刷可能接到「写之前发出」的 GET（force 被在途请求吸收；TOCTOU 丢更新）**

- **位置**：`web/js/blocks.js:19-28`——`if (inflight) return inflight;` 在 `force` 判定**之前**；调用点 `:124-126`（`blockOp` 写成功后 `ensureBlocks(true)`）。
- **机制**：若此刻已有在途 GET（page-load 首拉 / 前一次写的重取），force 被吞掉、直接复用**快照早于本次写**的响应 → `cache` 停在写前状态 → 订阅者立刻按旧快照重绘（`blockcard.js:290`）。陈旧持续到**下一次写**才被纠正。代码注释自述「进行中：复用同一请求（含 force 在途时）」——把复用写成了特性，但复用的响应可能早于本次写。
- **修法**：`force` 时不用在途请求（记 `pendingForce` 待落地后再发一次），或把 inflight 记成 `{promise, force}`。blame `2f50e413`（M3 期）。
- **severity：低危（low-med）｜ effort：XS｜ 来源：效率(BUG-F3-1) + 高度(附注1) + 质量(附注1)〔三透镜同判〕｜ confidence：medium（未实测，窗口 ms 级）**

**B5 · 块库卡载入失败被静默吞 → 永久停在「块库加载中…」**

- **位置**：`web/js/blockcard.js:291`（`ensureBlocks().then(...).catch(() => { /* 保持空态 */ })`），配合 `blockcard.js:166`（`if (!d) → '块库加载中…'`）。
- **机制**：`ensureBlocks()` 失败时既不重试也不显示错误，`cache` 保持 null → 卡永远显示「加载中」，用户无法区分「慢」与「坏了」；同一时刻块库条（`blocks.js:383-386`）却会打印「块库加载失败：…」——同一需求两种待遇。
- **修法**：catch 里写 `'块库加载失败：' + err.message`，并给一次重试入口。
- **severity：低危｜ effort：XS｜ 来源：效率(BUG-F3-3)｜ confidence：high**

**B6 · 后台刷新拆掉编辑中的行 → 触发「被动 blur 提交」（用户没确认过的写入）**

- **位置**：`web/js/bc-list.js:120-140`（`editRowInline` 的 textarea）+ `web/js/bc-ops.js:30`（`el0.addEventListener('blur', () => commit(true))`）+ `web/js/blockcard.js:160-179`（`draw()` 每次 `list.textContent=''` 全量重建）。
- **机制**：用户在块卡里就地编辑块 A（textarea 打开、`done=false`）→ 任何一次块写（含抽屉里「存为块」`blocks.js:392`、全局 Ctrl+Z 路径）→ `blockOp` → 广播 → `draw()` 清空列表 → 编辑中的 textarea 被移出文档 → 浏览器补发 blur → `inlineCommit(commit=true)` 把编辑器里的当前内容**直接写库**（用户本次没做确认动作），光标/半截输入随 DOM 一起消失。反证：不是「点外提交」口径（用户没有点外动作）；`done` 幂等闸只防重复提交，不防「被动 blur」。
- **修法**：`draw()` 前嗅探 `document.activeElement.closest('.bco-edit')`，对进行中的编辑抑制本次 blur 提交 + 把提交权交给重绘后的行（或先 `ctx.refresh()` 后重放编辑态）。
- **severity：低危（low-med）｜ effort：small｜ 来源：效率(BUG-F3-4)｜ confidence：medium**
